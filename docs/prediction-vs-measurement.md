> 实测结果追加在下方，预测原文不改。目的不是炫准确率，是区分

## 一、预测（先写，未跑）

配置与已有三档完全一致：Qwen3-4B-AWQ（AWQ 4-bit，权重 2.5 GiB）、
RTX 3060 Laptop 6GB（GDDR6，理论带宽 336 GB/s，按官方规格）、
`--max-model-len 2048 --gpu-memory-utilization 0.90 --enforce-eager`、
KV cache 15,232 tokens、48 请求 × (input 256 / output 128)、`--ignore-eos`。

### 依据

- **KV 算术**：per-token KV = 2(K+V) × 36 层 × 8 kv-heads × 128 dim × 2 B
  = 147,456 B/token。15,232 tokens × 147,456 B = 2.246 GB = 2.09 GiB ✓（与引擎日志一致）。
  c=8 时活跃 KV = 8 × 384 tokens × 147,456 B ≈ 452 MB ≪ 2.09 GiB → **KV 不是瓶颈**，
  吞吐由 decode 的权重读取 + AWQ 反量化开销决定，TTFT 由排队决定。
- **已有三档的边际量**：c1→c4 每加一个并发 +17.24 tok/s（19.99→71.71），
  c4→c16 每加一个 +15.81 tok/s（71.71→261.41）——边际递减很慢，
  说明 c≤16 内远未饱和；每请求速率从 19.99 滑到 16.34 tok/s（权重读取被摊薄、
  step 时间随 b 轻微增长）。
- **TTFT 排队**：c4→c16 的 p99 斜率 = (1796.0−481.2)/12 ≈ 110 ms/请求；
  c=8 介于两者之间，按同斜率外推。

### 预测值（区间 = 我认为的 15% 误差带）

| 指标 | c=8 预测 | c=16 复测预测 |
|---|---|---|
| 输出吞吐 tok/s | **135**（区间 128–142） | **261**（区间 248–275，允许 ×1.05 复现波动） |
| 总吞吐 tok/s | 405（=3×输出） | 784 |
| req/s | 1.05 | 2.04 |
| TTFT p99 ms | **920**（区间 850–1000） | **1796**（区间 1600–2000） |
| TPOT p99 ms | 70（区间 60–80，三档样本本身在 61.8–79.4 抖动） | 62 |

### 若偏差 >15%，我要解释的机制假设（预先写下，防止事后编）

1. **c=8 吞吐高于 140**：说明 c=4→16 之间不是线性而是超线性（调度器在
   batch=8 才吃满 SM），边际量估算失效——那意味着 c=4 档是被 prefill/decode
   比例卡住而不是模型饱和。
2. **c=8 TTFT p99 高于 1000**：说明 p99 尾部是排队尾效应（非均值线性），
   c=8 已经踩到「decode 独占 GPU 导致 prefill 饥饿」的区域。
3. **c=16 复测低于 248**：说明单次测量不可复现（<5% 波动假设不成立），
   卡片里所有单次读数都要降级为量级参考——这是比误差更大问题。

## 三、偏差机制解释（不许事后编，逐条对预测里写下的假设）

**假设 3 被直接触发，而且比预想严重**：同一 c=16、同一脚本、同 seed，
原始卡片 261.41 → 复测 298.52，跨次差 **+14.2%**。这证明单次扫描的读数
存在 ~14% 的 run-to-run 波动，卡片里所有绝对数值只能当量级参考；
「13.1× 并发扩展比」这种 *同一次 run 内* 的比值不受影响（分子分母同源），
但跨 run 的数字不能并排比。

**形状没被推翻**：把原曲线整体乘全局因子 1.1420（=298.52/261.41）后，
c=8 的线性插值为 154.10 tok/s，实测 162.48 → 仅 +5.4%（<15%）。
也就是说 c≤16 的边际线性/轻微超线性判断成立，预测错的是**全局速率因子**
而非调度形状。假设 1（batch=8 吃满 SM）只值那 5.4%，不是主因。

**TPOT 的超带也是同一个因子**：62 × (261.41/298.52) = 54.3 ms，
实测 53.06 → −2.4%。decode step 变快与吞吐变快同源，不是独立现象。
TTFT p99 两档都命中（+3.9% / −11.2%），因为排队主导的首 token 延迟
与 decode 速率因子耦合弱——这条是预测里没写、实测才看出的结构。

**全局因子从哪来（候选未区分，明确标 UNKNOWN）**：复测窗口
c=16 功率 70.67 W（sd 10.65，仅 21 个 1Hz 样本）vs 原卡 67.57 W；
GPU 复测前 15 MiB / 8% util / 无 compute-apps（Ollama 占用已释放）。
更可能是 SM clock / 功耗墙 / 热状态差异，但本轮没采 `clocks.sm`，
**不能归因**。要定论需第三次同条件复测并同时记录 SM clock、功率、
显存占用——这是卡片 v0.2 的明确待办，不是现在能讲的故事。

## 四、这一格改变了什么

- 卡片 README 的「单轮扫描」不再是隐含前提，而是显式限制：
  绝对数值 ±~14% 跨次波动；比值结论（同 run 内）仍可引用。
- 面试答法：被问「你这数能复现吗」→ 答「同一脚本同 seed 复测 c=16
  差 14.2%，所以我把它当量级参考；真正可复现的是同 run 内的比值和我
  先写预测再跑的闭环」——比假装数字精确更值钱。
- 按 LeCun 的判据，这一格是「测量学」而非「又跑一次 benchmark」：
  它用一个能打自己脸的对照，量出了自己卡片的不确定性。
